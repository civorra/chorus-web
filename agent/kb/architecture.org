#+DESCRIPTION: Global architecture of chorus-web: stack, module layout, data flows, ECA integration, Perl bridge, auth, Docker.

* Overview

Chorus Web (~chorus-web~) is a Node.js/Express web application acting as a GUI frontend
to the Chorus Engine pipeline.  It does NOT embed the Chorus Perl engine — it delegates
all inference and KB work to the ECA agent running in a separate ~eca-server~ container
via an HTTPS + SSE API.

| Layer       | Technology            | Entry point              |
|-------------+-----------------------+--------------------------|
| Backend     | Node.js + Express     | ~server.js~              |
| Frontend    | Vanilla JS / HTML5    | ~chorus-web.html/js/css~ |
| ECA client  | HTTPS + SSE (custom)  | ~eca-client.js~          |
| Perl bridge | ~child_process.spawn~ | ~server/helpers/perl.js~ |
| Auth        | OAuth PKCE / Docker   | ~auth.js~                |
| Containers  | Docker Compose        | ~docker-compose.yml~     |

* Data flow — normal request lifecycle

** Scan / read (GET)

#+BEGIN_EXAMPLE
browser
  → GET /api/sandboxes
  → scan.js router
  → chorus/scanner.js (scanAll / scanSandbox)
    → chorus/fs.js (readFileSafe, listDirs)
    → chorus/parser.js (parseSandboxReadme, extractOrgTable …)
    → chorus/reports.js (buildRunReportIndex, computeConvergenceFromRunReport)
    → chorus/thesaurus.js (scanSandboxThesaurus)
  ← JSON response
#+END_EXAMPLE

** ECA terminal (POST → SSE stream)

#+BEGIN_EXAMPLE
browser
  → POST /api/sandboxes/:sbId/terminal  { message, sessionId, level, … }
  → routes/terminal.js
    → chorus.scanSandbox() — build context block
    → eca.setChatAgent(chatId, agent)   — set expected agent (undocumented REST endpoint)
    → eca.subscribeEcaEvents(chatId)    — open SSE /api/v1/events BEFORE sending prompt
    → eca.ecaRequest('/api/v1/chats/:id/prompt', POST, { message })
    ↔ SSE events relayed to browser:
        chunk       — text fragment
        tool        — tool call info (classifyToolCall)
        ask         — eca__ask_user payload
        skill       — skill loaded (bandeau "Skill actif")
        taskboard   — eca__task state update
        ping        — keep-alive (every 15s)
        refresh     — trigger UI refresh on key file writes (WEB-021)
        thesaurus-restart / thesaurus-status — thesaurus-assistant lifecycle
        done / error — terminal finished
#+END_EXAMPLE

** Perl execution (SSE stream)

#+BEGIN_EXAMPLE
browser
  → POST /api/sandboxes/:sbId/projects/:projId/check   (or similar)
  → routes/projects.js (or terminal.js)
  → server/helpers/perl.js → child_process.spawn('perl', args, { cwd, env })
    → stdout/stderr lines → sseSend(res, 'log', { line })
    → close code 0 → onDone() → sseDone(res)
    → close code != 0 → sseError(res, …)
#+END_EXAMPLE

** Auth — credential resolution order

#+BEGIN_EXAMPLE
Priority (highest first):
  1. ECA OAuth native   → $CHORUS_HOME/../.eca/db.transit.json  (Transit/Clojure format)
  2. Webapp auth file   → $CHORUS_HOME/.webapp-auth.json         (plain JSON, mode 0600)
  3. Environment        → ANTHROPIC_API_KEY env var              (injected by eca-bootstrap.sh)

GET /api/auth/status reads all three sources and merges them (dedup by provider).
POST /api/auth/apikey writes to .webapp-auth.json and triggers Docker restart of eca-server.
POST /api/auth/reload-eca triggers Docker restart directly.
#+END_EXAMPLE

* ECA server integration

~eca-client.js~ owns ALL communication with the remote ~eca-server~ container.

| Function              | Purpose                                                        |
|-----------------------+----------------------------------------------------------------|
| ~ecaRequest~          | Generic HTTPS request (Bearer auth, ~agent:false~ per request) |
| ~pingTcp~             | TCP-only health probe — avoids Jetty 12 HTTP bug in /health    |
| ~promptAndWait~       | Legacy polling mode (GET /chats/:id); Jetty bug fallback       |
| ~promptAndWaitSSE~    | Preferred one-shot mode via SSE — avoids Jetty bug entirely    |
| ~subscribeEcaEvents~  | Long-lived SSE /api/v1/events — multi-chat, sub-agent aware    |
| ~setChatAgent~        | POST /chats/:id/agent — undocumented REST endpoint (see §Pitfalls) |
| ~subscribeLoginFlow~  | Drives ECA native /login flow (device-code / PKCE)             |
| ~sendLoginStep~       | Sends a reply to an ask-question in a login flow               |

** SSE event model (~subscribeEcaEvents~)

- Opens a single persistent connection to ~/api/v1/events~ (global, all chats)
- Filters by parent ~chatId~ AND dynamically tracks sub-agent ~chatId~s (Axe 5)
- Sub-agent tool calls emitted on a separate ~subagent-<toolCallId>~ chatId — the
  parent's ~spawn_agent~ toolCallRun carries ~details.subagentChatId~ revealing it
- Tool names in SSE payloads are WITHOUT ~eca__~ prefix (confirmed empirically
  2026-10-13 — TOOL_FAMILIES map must NOT include "eca__" prefix, see §Pitfalls)

** Tool call classification (~classifyToolCall~)

Groups ~≈15 ECA tools into families: ~read~ · ~edit~ · ~shell~ · ~git~ · ~agent~ · ~task~ · ~skill~.
Extracts structured metadata: ~taskboard~ (eca__task details), ~isSubagent~,
~isSkillLoad~/~skillName~, ~path~ (write target, used by WEB-021 refresh trigger).

* Sandbox filesystem conventions

~SANDBOXES_DIR()~ defaults to ~/chorus/engine/sandboxes~ (overridable via ~SANDBOXES~ env var).

#+BEGIN_EXAMPLE
$SANDBOXES/<sbId>/

  agent/chorus/index.org             ← pipeline + integrated corpus table
  agent/chorus/<slug>.org            ← per-agent KB definition
  agent/.kb-hash                     ← sha256 of KB content (stale detection)
  rules/<slug>/<RNN>-*.yml           ← YAML inference rules
  corpus/                            ← normative source documents
  workspace/<entity>/
    <projId>.json                    ← imported + checked project (Flat convention)
    <projId>.label.json              ← display name sidecar (WEB-026)
    <projId>.thesaurus.json          ← project-level thesaurus Niveau 2 (WEB-027)
    thesaurus.org                    ← entity-level thesaurus Niveau 3
    reports/
      run-report-*.json              ← Chorus pipeline output (chorus-check)
      explain-*.md / synthese-*.md   ← ECA-generated reports
      import-report-*.org            ← chorus-import-project trace
      audit-import-*.md              ← chorus-audit-import report
  .last-check-results.json           ← chorus-check --all cache (kb_hash + convergence)
  .last-strengthen-report.json       ← chorus-strengthen gap report
  .last-fix-history.json             ← chorus-fix patch history

* Thesaurus — 3-tier architecture

| Tier | File                                      | Scope   | Managed by               |
|------+-------------------------------------------+---------+--------------------------|
|  Niv 2 | ~workspace/<entity>/<projId>.thesaurus.json~ | Project | thesaurus-assistant ECA skill |
|  Niv 3 | ~workspace/<entity>/thesaurus.org~          | Entity  | Webapp 🏢 button only    |
|  Global | ~agent/thesaurus/global.org~               | Sandbox | chorus-import-project    |

⛔ The ECA thesaurus-assistant skill MUST NEVER write to thesaurus.org § Aliases —
entity promotion is exclusively via the webapp 🏢 button (ENG-071).

** Sections per thesaurus file

| Section          | File               | Managed by                                      |
|------------------+--------------------+-------------------------------------------------|
| ~* Aliases — type_element~ | Niv 3 .org | Webapp 🏢 (entity-promote) + legacy imports  |
| ~* Aliases — slot values~  | Niv 3 .org | Webapp 🏢 (entity-promote) + legacy imports  |
| ~* Pending~      | Niv 3 .org         | Legacy pre-ENG-071 · ~unconfirmThesaurusAlias~ transitoire |
| ~* Out-of-scope~ | Niv 3 .org         | Skill (reject decision) · ~resolveThesaurusPending(reject)~ |
| ~* Conflicts~    | Niv 3 .org         | Skill (mapping collision cross-import) — **⚠️ non extrait par scanSandboxThesaurus** |
| ~aliases_type_element~ | Niv 2 JSON  | Skill / ~resolveThesaurusPending(confirm)~ (projet)  |
| ~aliases_slot_values~  | Niv 2 JSON  | Skill / ~resolveThesaurusPending(confirm)~ (projet)  |
| ~pending~         | Niv 2 JSON         | Skill (ENG-071) — toute nouvelle entrée ⚠️           |
| ~out_of_scope~    | Niv 2 JSON         | ~_resolvePendingFromProjectJson(reject)~              |

** Thesaurus lifecycle (contraintes de cohérence)

#+BEGIN_EXAMPLE
1. Premier import
   chorus-import-project Phase 3
   → ✅ certain    → Niveau 2 JSON § aliases_type_element / aliases_slot_values
   → ⚠️ nouveau    → Niveau 2 JSON § pending   (⛔ JAMAIS thesaurus.org § Pending — ENG-071)
   → ⬜ hors-pér.  → Niveau 3 org § Out-of-scope
   → ⚠️ conflit    → Niveau 3 org § Conflicts  (⚠️ invisible dans la webapp — P-18)

2. Résolution manuelle webapp (onglet Thésaurus)
   a) Via "Assistant" (thesaurus-assistant ECA skill)
      → ✅ Confirmer → Niveau 2 JSON § aliases  (⛔ JAMAIS thesaurus.org § Aliases)
      → ⬜ Hors périmètre → Niveau 3 org § Out-of-scope
      → ⏭️ Passer  → reste dans Niveau 2 JSON § pending
   b) Via confirmation unitaire (webapp resolveThesaurusPending)
      → ✅ Confirmer (projet) → Niveau 2 JSON § aliases  (useLevel2=true)
      → ✅ Confirmer (entity) → Niveau 3 org § Aliases  (entityPromote=true)
      → ❌ Rejeter → Niveau 3 org § Out-of-scope

3. Promotion entity (bouton 🏢 — irréversible)
   → Niveau 3 org § Aliases — IMMUABLE (guard structurel dans unconfirmThesaurusAlias)
   → ⛔ Jamais annulable depuis la webapp une fois promu

4. Annulation d'un alias confirmé (bouton ↩️)
   → Niveau 2 : supprimé de Niveau 2 JSON § aliases
                + réinséré dans Niveau 3 org § Pending  ← état transitoire (voir P-16)
                + _detectProjectJsonDrift → driftedElements retourné (voir P-17)
   → Niveau 3 : REFUSÉ (guard structurel — entity-promoted = définitif)

5. Ré-import (obligatoire pour refléter les changements thésaurus dans le JSON projet)
   → Phase 1.2b lit thesaurus.org § Aliases + Niveau 2 JSON § aliases → appliqués à ✅ confiance
   → Phase 1.2b lit thesaurus.org § Pending → traités comme ⚠️ (incluant les entrées issues de unconfirm)
   → Niveau 2 JSON § pending → traités via _a_confirmer tier logic
   → Produit un JSON projet elements[] à jour avec l'état thésaurus courant

   ⚠️ RÈGLE : tout changement thésaurus (confirm/unconfirm/promote) n'est visible dans
   elements[] du JSON projet QU'APRÈS un ré-import. hasUnintegratedThesaurus=true signal.

6. Thesaurus-assistant (fin de session obligatoire)
   → Draine thesaurus.org § Pending : résout ou transfère vers Niveau 2 JSON § pending
   → Garantit que thesaurus.org § Pending est vide à la fin (ENG-071 restauré)
#+END_EXAMPLE

** Pending dual-source (thesaurus.org + JSON projet)

Après ENG-071, les entrées Pending doivent être en Niveau 2 JSON.  En pratique deux
sources coexistent et le ~thesaurus-assistant~ doit les deux drainer :

| Source | Origine | État |
|--------+---------+------|
| ~<projId>.thesaurus.json § pending~ | Import post-ENG-071 | Nominal (ENG-071 compliant) |
| ~thesaurus.org § * Pending~ | Legacy pre-ENG-071 · ~unconfirmThesaurusAlias~ | Transitoire (voir P-16) |

Le ~thesaurus-assistant~ garantit qu'à la fin de chaque session, ~thesaurus.org § * Pending~
est vide — les entrées non résolues y sont transférées vers ~<projId>.thesaurus.json § pending~.

* Docker deployment

~docker-compose.yml~ defines two services:
- ~chorus-web~ — this Node.js app (port 3000, mounts CHORUS_HOME and Docker socket)
- ~eca-server~  — ECA headless server (port 7777, TLS self-signed *.local.eca.dev)

~eca-bootstrap.sh~ runs at container startup: injects ~ANTHROPIC_API_KEY~ from
~$CHORUS_HOME/.webapp-auth.json~ if present; falls back to env var.

~auth.js~ triggers Docker socket restart of ~eca-server~ after any credential change:
~POST /containers/<name>/restart~ on ~/var/run/docker.sock~ (mounted read-write).

* Frontend caching — no-store rule

All three frontend files (~chorus-web.html~, ~chorus-web.js~, ~chorus-web.css~) are
served with explicit ~Cache-Control: no-store, no-cache, must-revalidate~ headers.

Rationale (incident 2026-10-14): ~sendFile()~ applies ~Last-Modified/ETag~ by default;
some browsers/proxies do not revalidate on F5, keeping old JS active post-deploy.
The HTML file had the guard first; JS/CSS were added after the incident.
